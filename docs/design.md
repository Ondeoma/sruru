# 設計

## 全体

- アプリはステートレス。ブラウザのセッション・ログインの途中の状態・認可の要求・認可コード・トークン・署名鍵・定期処理のリースはすべて PostgreSQL にある。
  どのノードに振り分けられても同じように動く。
- 署名鍵（RS256・ES256）は `APP_SECRET` から作った鍵（AES-256-GCM）で暗号化して DB に保存する。各ノードは1分ごとに読み直すので、
  管理画面での鍵の入れ替えはほかのノードにもすぐ反映される。古い鍵は退役させるまで JWKS に残る（発行済みのトークンを検証できる）。
- 定期処理（メールの送信・期限切れの掃除・動的なグループの計算・ディレクトリの同期）は `job_lock` のリースで1ノードだけが動かす。

## ブラウザのセッションと複数のアカウント

- Cookie `sruru_session`（HttpOnly・SameSite=Lax）は `browser_sessions` を指す。1つのブラウザのセッションに複数の `logins`（アカウントごと）があり、
  `active_user` が使用中のアカウント。
- 画面からの更新系の API は `X-Sruru` ヘッダーが必要（CSRF 対策。SameSite=Lax と合わせて二重に防ぐ）。
- ログインが完了したら Cookie の値を新しくする（セッションの固定化の対策）。
- 要求の本文は 2MB まで（超えたら 413）。パスワードのハッシュ（Argon2id）は blocking のスレッドで計算する。
- グループの一覧は所属の計算でリクエストごとに使うので、各ノードで5秒だけ控える（そのノードでの変更ではすぐ捨てる）。

## ログインの流れ（`login_flows`）

1. 本人確認: パスワード / クライアント証明書（`/auth/cert`）/ 外部の IdP（`/auth/fed/{slug}`）。amr に `pwd`・`swk`・`fed` を記録。
2. パスワードの期限切れ・管理者の指定 → パスワードの変更。
3. 多要素認証が必要（ポリシーで必須・アプリで必須・本人が認証アプリを登録済み・多要素の追加）→ TOTP・メールのコード・回復コード。
   必須なのに未登録なら、その場で認証アプリを登録してもらう。済んだら amr に `mfa`。
4. 完了: `logins` を作って使用中にする。認可の要求の途中なら `/auth/resume?req=…` に戻る。

失敗は、ユーザーごと（連続の回数でロック）と IP アドレスごと（時間の窓の中の回数で一時的に拒否）に数える。
存在しないユーザーでも Argon2id の計算をして、応答時間でユーザーの有無が分からないようにしている。

## 認可（OIDC・SAML 共通の判定 `AuthGate`）

アプリの有効 → IP 制限（全体・アプリ）→ ログイン（`prompt=login`・`ForceAuthn`・`max_age`）→ アカウントの選択 →
利用できるグループ → 多要素認証（アプリで必須のとき）。画面での操作が要るときは、要求を `auth_requests` に保存して
ログインの画面などへ移り、終わったら `/auth/resume` で続きを行う。

## トークン

- アクセストークンは JWT（`typ: at+jwt`）。`jti` を `access_tokens` に記録し、失効・ユーザーの無効化を UserInfo・イントロスペクションで反映する。
- リフレッシュトークンは不透明な値（DB にはハッシュ）。使うたびに新しい値に替え、使用済みの値が再び使われたら系列（family）ごと失効させる。
  `offline_access` がなければログインに結び付き、ログアウトで失効する。
- 認可コードは60秒・1回限り。2回目に使われたら、そのコードで発行したトークンを失効させる（RFC 6749 4.1.2）。

## 属性の式（`core/Expr.scala`）

`{{ パス | フィルター:"引数" }}`。式1つだけなら値の型（リスト・真偽値・数値）のまま、文字と混ぜると文字列になる。
動的なグループの条件（`core/GroupRule.scala`）も同じ値（`user.…`）を使う。

## 監査ログ

各行は1つ前の行のハッシュを含めた SHA-256 を持つ。書き込みは advisory lock で直列にする（複数ノードでも鎖が分岐しない）。
管理画面の「改ざんを検査」で鎖をたどって確かめる。保存期間を過ぎた古い行を消したあとは、残っている最初の行から検査する。

## SCIM

ユーザー・グループを SCIM の JSON に変換し、PATCH はその JSON に操作を当ててから元に戻す。属性名は大文字小文字を区別しない。
Entra ID が送るパスなしの `{"name.givenName": "…"}` や `emails[type eq "work"].value` にも対応する。

## グループごとのポリシー（`shared/GroupPolicy.scala`）

全体のポリシー（`settings` の `policies`）に、ユーザーが所属するグループ（親を含む）の上書き（`groups.policy`）を重ねて、
そのユーザーに効くポリシーを作る（`Directory.policyFor`）。ユーザーが分かっている処理（ログインの各段階・パスワードの条件・
ロック・多要素認証・セッションの期限と無操作・IP 制限・メールの件名）は、すべてこれを使う。

- **セキュリティの項目は「より厳しい方」**。優先度は関係しない。最小の長さ・文字の種類・履歴は大きい方、有効期限・無操作の時間は
  0（制限なし）でない短い方、ロックは回数が少ない方・時間が長い方（0 = 管理者が解除するまでが最も厳しい）、多要素認証は
  off < optional < required の強い方、使える方法は禁じた方（両方禁じたら認証アプリは残す）、ログインの有効期間・同時のアカウント数は小さい方。
  IP は、グループの allow にも含まれること（全体の allow と両方）、deny は足し合わせる。
- **表示の項目（サービス名・ロゴ）はグループが優先**。上書きしているグループのうち優先度（`groups.priority`）の大きいもの、
  同じなら名前の順で先のもの。ログインの前の画面は全体の表示、ログインした後は使用中のアカウントのもの（`/api/client-config`）。
- ユーザーに依らない項目（IP ごとの試行の制限・管理画面の IP・信頼するプロキシ・証明書・自己登録・Gravatar・監査ログ）は全体だけ。
- ロゴは `brand_logos` に保存し、`/brand-logos/{id}` で配信する（中身は変わらないので長く控えてよい）。SVG はスクリプト・イベントの属性・
  外部の参照を含むものを拒否し、配信のときも `sandbox` の CSP を付ける。どこからも使われなくなったロゴは、1日たってから掃除で消す。
- 無操作の時間がユーザーごとに違うので、掃除は全体とグループのうち最も短い時間を過ぎたログインを候補にして、ユーザーごとに判定する。

## 乗っ取りを防ぐための決まり

- **API トークンでできないこと**: パスワード・認証アプリ・回復コード・証明書・メールアドレスの変更と、トークンの作成は画面（Cookie）からだけ。
  管理者の操作も同じで、admin のトークンでは他人のパスワード・多要素認証・証明書・トークン・メールアドレスを変えられない。
  漏れたトークンからアカウントを乗っ取れないようにする。全体の IP の許可・拒否はトークンにも効く。
- **直近のログイン**: 本人がメールアドレス・認証アプリ・回復コード・証明書・トークンを変えるときは、10分以内にログインしたことを求める
  （401 と `X-Sruru-Reauth: 1`。画面はログインの画面へ移る）。盗まれた Cookie だけでは乗っ取りを長引かせる変更をさせない。
- **証明書の登録**: 本人が登録できるのは、その要求で提示した（秘密鍵を持っている）、信頼する CA の証明書だけ。
- **メールアドレス**: 本人が変えるときは他のユーザーと重ならないこと。確認のリンクは、求めたときのアドレスに結び付ける。
  未確認のアドレスは、外部 IdP との結び付け・証明書の対応付け・OIDC の `sub`（email モード）・動的グループの条件に使わない。
- **管理者になるグループ**（自身か親が管理者のグループ）には、動的なメンバーを付けない。SCIM では管理者のユーザー・グループを変えない。
- **Entra**: 許可リストにはテナント ID を書く。メールアドレスは、許可したテナントのときだけ信頼する（マルチテナントでは他のテナントの管理者がメールの属性を書けるため）。
- **ログインの失敗の回数**は、多要素認証まで終わってから戻す。メールのコードの試行は、確認と加算を1つの SQL で行う。
  ロック中はパスワードを確かめず、応答も同じ（ロック中の総当たりを防ぐ）。IP ごとの回数は、IPv6 を /64 にまとめて数える。
  メールでの2つ目の要素は、確認済みのアドレスだけに送る。
- **パスワードの変更（期限切れ・管理者の指定）**は多要素認証の後。多要素の追加（stepUp）では求めない。
  パスワードを変えたら、ほかのログインと、offline_access を含むトークンを失効させる。
- **認可の要求の印**（同意した・アカウントを選んだ）は、ブラウザのセッションとユーザーに結び付ける。再認証（prompt=login・ForceAuthn）は、要求の後にログインしたかを認証の時刻で判定する。
- **認可コード**は、持ち主のクライアントにしか見えない。コードから出したリフレッシュトークンはコードごとの系列にし、
  再利用のとき（期限の後でも）はその系列（offline_access も）と、同じアプリ・ユーザーのアクセストークンを失効させる。
- **ログインの終わり**: ログアウト・無操作・期限切れ・管理者の操作のどれでも `Directory.endLogin` を通し、トークンの失効と
  バックチャネルのログアウトを必ず一緒に行う。リフレッシュは、結び付いたログインが続いているときだけ。
  UserInfo・イントロスペクションは、アプリの無効化とアクセスグループからの除外をすぐ反映する。
- **ログアウト**: OIDC は `id_token_hint` がない GET では確認を挟む。SAML は署名のない要求なら SessionIndex が必須。
  SAML の SessionIndex は SP ごとに違う値（ほかの SP のものを推測できない）。署名付きで SessionIndex がない要求は、NameID が
  使用中のアカウントのものと同じときだけ。実際にログアウトしたときだけ Success を返す。
  ほかのサイトからの POST には SameSite=Lax の Cookie が付かないので、Cookie がなければ同じサイトから POST し直す。
- **SAML の要求**は IssueInstant が必須で、±300 秒まで。応答とアサーションの少なくとも一方は署名する。ACS・SLO は http(s) だけ。
- **SAML の HTTP-Redirect**: 署名を確かめるのと同じ解析で値を取り出し、キーの重複（符号化したキーを含む）を拒否する。SHA-1 は受け付けない。
- **SCIM**: 管理者の所属は SCIM では変えない（グループのメンバーの置き換えでも残す）。フィルターは 4096 文字・かっこ 32 段まで。
- **外部への通信**: 上流の IdP の issuer・設定で返る URL は https だけ（開発用の http://localhost を除く。ホストで判定する）。
  issuer か種類を変えたら、シークレットの入れ直しを求める。Google の token_uri は既定のものだけ。応答は 32MB まで。
- **CSP**: 画面のスクリプトは `'self'` だけ（インラインのスクリプトを許さない）。公開の URL が https なら HSTS を付ける。
- **起動の検査**: 本番（DEV_MODE でない）では、APP_SECRET・DATABASE_PASSWORD が例示の値（change-me）なら起動しない。
