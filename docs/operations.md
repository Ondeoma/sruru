# 構築・運用

## 推奨構成（3台）

各 VM に sruru アプリ・Patroni（PostgreSQL 17）・etcd・HAProxy・keepalived を置き、VIP で受けます。設定のひな形は `deploy/vm/`。

```
             VIP 10.0.0.10 (keepalived)
                     │ HAProxy（TLS 終端・クライアント証明書の受け取り）
        ┌────────────┼────────────┐
     sruru1       sruru2       sruru3        ← ステートレス（どこに振り分けてもよい）
        └────── PostgreSQL（Patroni: 1台がプライマリ、2台がレプリカ）──────┘
```

- アプリの `DATABASE_URL` には3台を並べ、`targetServerType=primary` を付けます。フェイルオーバー後は自動で新しいプライマリにつながります。
- `/healthz` は DB のプライマリに書けないとき 503 を返すので、HAProxy のヘルスチェックに使います。
- `APP_SECRET`・`PUBLIC_URL` は全ノードで同じにします。

試験用の3ノード構成（Docker）:

```bash
scripts/ha-up.sh     # 入口 http://localhost:9191
scripts/ha-test.sh   # アプリ1台の停止・DB のフェイルオーバーの試験
```

## 初期設定

1. 起動のログに出る「セットアップのトークン」で、画面の `/setup` から最初の管理者を作ります（管理者が1人もいないときだけ使える）。
2. 管理画面の「ポリシー」で、パスワード・ロック・多要素認証・IP 制限・サービス名・ロゴを決めます。
   部署などで変えたいときは、グループの画面の「ポリシーの上書き」で、そのグループの分だけ厳しくしたり、サービス名・ロゴを変えたりできます。
   ロードバランサーの後ろに置くときは、「信頼するプロキシ」に HAProxy のアドレスを入れます（X-Forwarded-For を使うため）。
3. メール（SMTP）を設定すると、メールのワンタイムコードとパスワードの再設定が使えます。

## クライアント証明書

- HAProxy で TLS を終端し、`deploy/vm/haproxy.cfg` のように `verify optional` と `X-SSL-Client-Cert` ヘッダーで渡します。
  ポリシーの「クライアント証明書」を有効にし、ヘッダー名と対応付けの方法（登録した証明書・SAN のメール・UPN・CN）を選びます。
- 管理画面の「証明書」で、利用者の証明書を発行する認証局（PEM）を登録します。
- sruru 自身で TLS を受けるときは `TLS_KEYSTORE`（PKCS#12）を設定します（クライアント証明書を求めるが、なくても接続できる）。

## バックアップ

- PostgreSQL を pgBackRest などでバックアップします（`deploy/vm/pgbackrest.conf`）。sruru の状態はすべて DB にあります。
- `APP_SECRET` も安全な場所に控えてください。失うと署名鍵・外部 IdP のシークレット・TOTP の鍵を読めなくなります
  （署名鍵は作り直せますが、利用者は認証アプリの登録をやり直すことになります）。

## 鍵の入れ替え

管理画面の「署名鍵」で入れ替えると、新しい鍵で署名し始めます。古い鍵は JWKS に残るので、発行済みのトークンはそのまま使えます。
アクセストークン・ID トークンの有効期間（既定1時間）が過ぎてから、古い鍵を退役させてください。
SAML の証明書は RS256 の鍵に付いているので、入れ替えたら SP にメタデータを登録し直してもらいます。

## 監視

- `/healthz`（DB のプライマリへの書き込み）
- 監査ログ: `login.failure`・`user.locked`・`policies.update`・`key.rotate` など。管理画面の概要に今日の失敗の数が出ます。
