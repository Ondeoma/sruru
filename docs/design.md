# 設計

## 全体

- アプリはステートレス。ブラウザのセッション・ログインの途中の状態・認可の要求・認可コード・トークン・署名鍵・定期処理のリースはすべて PostgreSQL にある。
  どのノードに振り分けられても同じように動く。
- 署名鍵（RS256・ES256）は `APP_SECRET` から作った鍵（AES-256-GCM）で暗号化して DB に保存する。各ノードは1分ごとに読み直すので、
  管理画面での鍵の入れ替えはほかのノードにもすぐ反映される。古い鍵は退役させるまで JWKS に残る（発行済みのトークンを検証できる）。
- 定期処理（メールの送信・期限切れの掃除・動的なグループの計算・ディレクトリの同期）は `job_lock` のリースで1ノードだけが動かす。

## ブラウザのセッションと複数のアカウント

- Cookie `sruru_session`（HttpOnly・SameSite=Lax）は `browser_sessions` を指す。1つのブラウザのセッションに複数の `logins`（アカウントごと）があり、
  `active_user` が使用中のアカウント。
- 画面からの更新系の API は `X-Sruru` ヘッダーが必要（CSRF 対策。SameSite=Lax と合わせて二重に防ぐ）。
- ログインが完了したら Cookie の値を新しくする（セッションの固定化の対策）。
- 要求の本文は 2MB まで（超えたら 413）。パスワードのハッシュ（Argon2id）は blocking のスレッドで計算する。
- グループの一覧は所属の計算でリクエストごとに使うので、各ノードで5秒だけ控える（そのノードでの変更ではすぐ捨てる）。

## ログインの流れ（`login_flows`）

1. 本人確認: パスワード / クライアント証明書（`/auth/cert`）/ 外部の IdP（`/auth/fed/{slug}`）。amr に `pwd`・`swk`・`fed` を記録。
2. パスワードの期限切れ・管理者の指定 → パスワードの変更。
3. 多要素認証が必要（ポリシーで必須・アプリで必須・本人が認証アプリを登録済み・多要素の追加）→ TOTP・メールのコード・回復コード。
   必須なのに未登録なら、その場で認証アプリを登録してもらう。済んだら amr に `mfa`。
4. 完了: `logins` を作って使用中にする。認可の要求の途中なら `/auth/resume?req=…` に戻る。

失敗は、ユーザーごと（連続の回数でロック）と IP アドレスごと（時間の窓の中の回数で一時的に拒否）に数える。
存在しないユーザーでも Argon2id の計算をして、応答時間でユーザーの有無が分からないようにしている。

## 認可（OIDC・SAML 共通の判定 `AuthGate`）

アプリの有効 → IP 制限（全体・アプリ）→ ログイン（`prompt=login`・`ForceAuthn`・`max_age`）→ アカウントの選択 →
利用できるグループ → 多要素認証（アプリで必須のとき）。画面での操作が要るときは、要求を `auth_requests` に保存して
ログインの画面などへ移り、終わったら `/auth/resume` で続きを行う。

## トークン

- アクセストークンは JWT（`typ: at+jwt`）。`jti` を `access_tokens` に記録し、失効・ユーザーの無効化を UserInfo・イントロスペクションで反映する。
- リフレッシュトークンは不透明な値（DB にはハッシュ）。使うたびに新しい値に替え、使用済みの値が再び使われたら系列（family）ごと失効させる。
  `offline_access` がなければログインに結び付き、ログアウトで失効する。
- 認可コードは60秒・1回限り。2回目に使われたら、そのコードで発行したトークンを失効させる（RFC 6749 4.1.2）。

## ネイティブアプリ（RFC 8252）とデバイスフロー（RFC 8628）

ネイティブアプリは公開クライアント（シークレットなし）で、システムのブラウザから認可コード + PKCE（S256. 公開クライアントは必須）を使う。

- **リダイレクト URI の照合**（`core/RedirectUris.scala`）: 登録した文字列との完全一致。公開クライアントに限り、`http://127.0.0.1` と `http://[::1]` の URI は
  ポートだけの違いを許す（RFC 8252 7.3。アプリは空いているポートを OS からもらう）。スキーム・ホスト・パス・クエリは完全一致で、ユーザー情報・フラグメント付きは対象外。
  `localhost` は完全一致のまま（RFC 8252 8.3）。機密クライアントは戻り先が決まっているので、ループバックでも完全一致だけ。
  認可コードには実際に要求された値（ポートまで）を結び付け、トークンの交換では完全一致で確かめる。
- **ログアウト後の URI**（`OidcRoutes.allowedPostLogout`）: 登録したループバックの URI とポートだけ違うものは許す（公開クライアントだけ。パスは完全一致）。
  「登録したリダイレクト URI と同じオリジンなら任意のパス」のほうは、ポートの違うループバックには広げない（ポートが違えば別のオリジン。戻り先を必要以上に増やさない）。
- **カスタムスキームへの戻り**: 認可の結果は、`/oauth2/authorize`（ログイン済みのとき）か `/auth/resume`（ログイン・同意の後。画面は `location` でここへ移る）の
  303 の `Location` で返す。フォームの送信ではないので、CSP の `form-action` は効かない。フォームを送信した後にリダイレクトする経路は
  ログアウトの確認の画面（`/oauth2/logout`）だけで、ここは `form-action` に戻り先のスキームを足す（Chromium は送信後のリダイレクトにも `form-action` を当てる）。

デバイスフロー（`DeviceRoutes`・`DeviceStore`・表 `device_codes`）は、「デバイスコード」のグラントを選んだクライアントだけが使える。

1. 端末が `POST /oauth2/device_authorization` を呼ぶ（クライアントの認証はトークンのエンドポイントと同じ）。`device_code`（256 ビットの乱数。DB には SHA-256）と
   `user_code`（母音と紛らわしい文字を除いた 20 文字から 8 文字。`BCDF-GHJK`）を作る。有効期限は 10 分、ポーリングの間隔は 5 秒。
2. 利用者が `/device`（`verification_uri`。要求を受けたホスト名のもの）を開く。コードの入力（`POST /api/device/verify`）にはログインが要る。
   合っていれば `auth_requests` に `protocol = device` の要求を作り、通常の認可と同じ `/auth/resume` → `AuthGate`（アプリの有効・IP 制限・
   利用できるグループ・多要素認証の step-up）を通す。通ったら許可／拒否の画面（`/device?req=…`）へ移る。
   `verification_uri_complete`（コード付き）で開いても、入力の欄が埋まるだけで、この画面は省かない（フィッシング対策。RFC 8628 5.4）。
3. 許可／拒否（`POST /api/device/decide`）。許可はもう一度 `AuthGate` を通してから、利用者・ログイン・認証の時刻・amr を `device_codes` に記録する。
   要求は、コードを入力したブラウザのセッションと利用者に結び付けてあり（`verifiedBy`）、ほかのブラウザ・アカウントからは決められない。
   デバイスフローの許可は、同意の記録（`consents`）には残さない（次回も必ず尋ねる）。
4. 端末は `POST /oauth2/token`（`grant_type=urn:ietf:params:oauth:grant-type:device_code`）で尋ねる。行をロックして判定し、
   `authorization_pending`・`slow_down`（前回から間隔より早い。間隔を 5 秒延ばす）・`access_denied`・`expired_token` を返す。
   許可済みなら使用済みにして、認可コードと同じ発行の処理（ID トークン・アクセストークン・リフレッシュトークン。`offline_access` の扱いも同じ）を通す。
   発行の前に、利用者の無効化・グループからの除外・ログインの終了を確かめる。使用済みの `device_code` がもう一度使われたら、そのとき出したトークンを失効させる。

歯止め:

- **user_code の総当たり**: 誤った入力（形の違うものも）を、利用者ごと（15 分に 10 回）と IP ごと（15 分に 30 回）に `login_throttle` で数え、
  上限に達したら正しいコードも受け付けない。入力はログインした利用者だけができるので、試行は必ずアカウントに結び付く。失敗は監査ログ（`device.verify`）に残る。
- **開始のエンドポイント**: 同じ IP の多くの端末からまとめて呼ばれるのが正常なことがあるので、IP ごとの回数では数えない。代わりに、
  未完了（許可も拒否もされておらず、期限内）の要求の件数に上限を置く（クライアントごとに 500 件・全体で 5000 件。超えたら 429）。
  全体の上限は、当てずっぽうの `user_code` が当たる確率（未完了の件数 ÷ 20^8）も抑える。公開クライアントの `client_id` は秘密ではないので、
  そのクライアントの枠を他人が埋めることはできる（影響はそのクライアントのデバイスフローだけで、10 分で空く）。
- 期限切れの行は定期の掃除で消す（トークンを発行した行は、再利用を検出できるよう 1 日残す）。
- マルチドメイン: `device_codes.domain` に要求を受けたドメインを残し、コードの入力・許可・トークンの発行を同じドメインでだけ行う。
- 監査ログ: `device.start`（開始）・`device.approve`（許可）・`device.deny`（拒否）・`device.verify`（コードの入力の失敗）。

## 属性の式（`core/Expr.scala`）

`{{ パス | フィルター:"引数" }}`。式1つだけなら値の型（リスト・真偽値・数値）のまま、文字と混ぜると文字列になる。
動的なグループの条件（`core/GroupRule.scala`）も同じ値（`user.…`）を使う。

## 監査ログ

各行は1つ前の行のハッシュを含めた SHA-256 を持つ。書き込みは advisory lock で直列にする（複数ノードでも鎖が分岐しない）。
管理画面の「改ざんを検査」で鎖をたどって確かめる。保存期間を過ぎた古い行を消したあとは、残っている最初の行から検査する。

## SCIM

ユーザー・グループを SCIM の JSON に変換し、PATCH はその JSON に操作を当ててから元に戻す。属性名は大文字小文字を区別しない。
Entra ID が送るパスなしの `{"name.givenName": "…"}` や `emails[type eq "work"].value` にも対応する。

## グループの親子（`group_parents`）

- 親は複数にできる（有向非巡回グラフ）。子のメンバーは、すべての親（とその祖先）のメンバーでもある（`Membership.expand`）。
  菱形に同じ祖先へたどり着いても、所属は1回だけ数える。
- 親を変えるときは、親たちの祖先に自分がいないか（循環）を確かめる。自分を親にはできない（DB の check 制約でも禁じる）。
- 祖先のどれかが管理者のグループなら、メンバーは管理者になる。そのため、条件（動的なメンバー）を付けるグループは、
  管理者のグループ（またはその子）の下に置けない（保存のときに拒否. 後から親が管理者になった場合も、`ruleUsable` で条件を使わない）。
- 画面の一覧（木）では、親が複数あるグループをそれぞれの親の下に出す。チェックボックスなどの選択肢では1回だけ、名前の順で最初の親の下に出す。

## グループごとのポリシー（`shared/GroupPolicy.scala`）

全体のポリシー（`settings` の `policies`）に、ユーザーが所属するグループ（親を含む）の上書き（`groups.policy`）を重ねて、
そのユーザーに効くポリシーを作る（`Directory.policyFor`）。ユーザーが分かっている処理（ログインの各段階・パスワードの条件・
ロック・多要素認証・セッションの期限と無操作・IP 制限・メールの件名）は、すべてこれを使う。

- **セキュリティの項目は「より厳しい方」**。優先度は関係しない。最小の長さ・文字の種類・履歴は大きい方、有効期限・無操作の時間は
  0（制限なし）でない短い方、ロックは回数が少ない方・時間が長い方（0 = 管理者が解除するまでが最も厳しい）、多要素認証は
  off < optional < required の強い方、使える方法は禁じた方（両方禁じたら認証アプリは残す）、ログインの有効期間・同時のアカウント数は小さい方。
  IP は、グループの allow にも含まれること（全体の allow と両方）、deny は足し合わせる。
- **表示の項目（サービス名・ロゴ）はグループが優先**。上書きしているグループのうち優先度（`groups.priority`）の大きいもの、
  同じなら名前の順で先のもの。ログインの前の画面は全体の表示、ログインした後は使用中のアカウントのもの（`/api/client-config`）。
- ユーザーに依らない項目（IP ごとの試行の制限・管理画面の IP・信頼するプロキシ・証明書・自己登録・Gravatar・監査ログ）は、
  グループでは上書きできない（一部はドメインで上書きできる。下の「マルチドメイン」）。
- ロゴは `brand_logos` に保存し、`/brand-logos/{id}` で配信する（中身は変わらないので長く控えてよい）。SVG はスクリプト・イベントの属性・
  外部の参照を含むものを拒否し、配信のときも `sandbox` の CSP を付ける。どこからも使われなくなったロゴは、1日たってから掃除で消す。
- 無操作の時間がユーザーごとに違うので、掃除は全体とグループのうち最も短い時間を過ぎたログインを候補にして、ユーザーごとに判定する。

## マルチドメイン（ホスト名ごとのポリシー. `shared/DomainPolicy.scala`・`api/Site.scala`）

同じ sruru を複数のホスト名で公開し、**アクセスしたホスト名**（ドメイン）ごとにポリシーと表示を変える。
ドメインは管理画面の「ドメイン」で登録する（`domains` の表。ホスト名は `host` か `host:port`）。`PUBLIC_URL` のホスト名が「既定」で、
行を持たない。登録のないホスト名で来た要求は、既定のホスト名として扱う。

- **データは共有**: ユーザー・グループ・アプリケーション・管理者・署名鍵・クライアントの登録は全ホスト名で 1 組。テナントの分離ではない。
  同じユーザーがどのホスト名からでもログインできる（絞りたければ、ドメインの IP 制限などで絞る）。
- **ホスト名の判定**（`Domains.resolve`）: `Host` ヘッダー。信頼するプロキシ（全体のポリシー）からの要求なら `X-Forwarded-Host` を先に見る。
  要求ごとにミドルウェアが `Site`（ファイバーごとの値）に入れ、`PolicyService.get`（ポリシー）と `ApiConfig.url`（公開 URL）がそれを読む。
  定期処理など要求の外では既定。スキームは `PUBLIC_URL` と同じ。
- **issuer・URL はホスト名ごと**: OIDC の discovery・`iss`（ID トークン・アクセストークン・認可の応答・ログアウトのトークン）、
  SAML のエンティティ ID・SSO・SLO の URL、SCIM の `location`、メールのリンク、アイコン・ロゴの URL、外部 IdP のリダイレクト URI は、
  アクセスしたホスト名のもの。各サービスには、使いたいポリシーのホスト名の URL を issuer として設定する。
  外部 IdP をドメインからも使うなら、そのホスト名のリダイレクト URI も外部 IdP に登録する。
- **重ねる順は 全体 → ドメイン → グループ**。ドメインの上書きは、指定した項目を全体の値と**置き換える**（緩めることもできる。
  アクセスするホスト名は常に 1 つなので、グループのように「厳しい方」でまとめる必要がない）。その結果に、グループの上書きを
  これまでどおり「厳しい方」で重ねる。緩いドメインはそのまま入口になるので、そのホスト名の IP 制限・公開範囲で守るのは管理者の責任。
- **上書きできる項目**: グループと同じ項目（パスワードの条件・ロック・多要素認証・セッション・IP の許可と拒否・サービス名・ロゴ）と、
  ログインの画面の案内・自己登録の可否・クライアント証明書でのログインの可否・使える外部 IdP（絞る）・管理機能の可否。
  ホスト名はログインの前から分かるので、ログインの画面（`/api/client-config`）・IP 制限・自己登録などログインの前の処理にも効く。
  IP の許可・拒否は、上書きすると全体の許可・拒否の代わりになる。有効期限・無操作の時間は 0（無期限・切れない）も指定できる。
  信頼するプロキシ・利用者のアドレスのヘッダー・管理画面の IP・IP ごとの試行の制限・証明書の対応付け・Gravatar・監査ログ・
  多要素認証を必須にするグループは全体だけ。
- **管理機能の可否**: 閉じたドメインでは、管理者でも管理画面・管理 API を使えない（403 `SRURU-1017`。画面にも「管理」を出さない）。
  いま開いているドメインについては、自分を締め出す設定（管理機能を閉じる・いまの IP を許可しない・削除）を受け付けない。
- **セッション・トークンはドメインに結び付ける**: ブラウザのセッション（`browser_sessions.domain`）・認可の要求・認可コード・
  リフレッシュトークン・アクセストークンは、作ったときのドメインを持ち、同じホスト名でだけ使える。Cookie はホスト名ごとに別なので
  ログインもホスト名ごとだが、Cookie の値をほかのホスト名に持ち込んでも見つからない。認可コード・リフレッシュトークンは
  発行したホスト名のトークンのエンドポイントでだけ交換でき、アクセストークンは `iss` が同じホスト名の UserInfo・イントロスペクションでだけ通る
  （緩いポリシーのホスト名で得たログイン・トークンを、厳しいホスト名を issuer にしているサービスに持ち込めない）。
  バックチャネルのログアウトの `iss` は、そのトークンを出したホスト名のもの。API トークン（`sruru_…`）はホスト名に結び付けず、
  使ったホスト名のポリシー（IP 制限）が効く。
- **ホスト名は後から変えられない**（消して作り直す）。ドメインを消すと、そのホスト名でのログインを終わらせる
  （トークンの失効とバックチャネルの通知も行う）。発行済みのトークンは、ホスト名が既定の扱いになるので通らなくなる。
- 無操作の時間の掃除は、全体・ドメイン・グループのうち最も短い時間を過ぎたログインを候補にして、ログインしたドメインとユーザーごとに判定する。
- 動的なグループの計算は、どのホスト名から操作しても同じ結果になるよう、全体のポリシーと既定のホスト名の URL で行う。

## 乗っ取りを防ぐための決まり

- **API トークンでできないこと**: パスワード・認証アプリ・回復コード・証明書・メールアドレスの変更と、トークンの作成は画面（Cookie）からだけ。
  管理者の操作も同じで、admin のトークンでは他人のパスワード・多要素認証・証明書・トークン・メールアドレスを変えられない。
  漏れたトークンからアカウントを乗っ取れないようにする。全体の IP の許可・拒否はトークンにも効く。
- **直近のログイン**: 本人がメールアドレス・認証アプリ・回復コード・証明書・トークンを変えるときは、10分以内にログインしたことを求める
  （401 と `X-Sruru-Reauth: 1`。画面はログインの画面へ移る）。盗まれた Cookie だけでは乗っ取りを長引かせる変更をさせない。
- **証明書の登録**: 本人が登録できるのは、その要求で提示した（秘密鍵を持っている）、信頼する CA の証明書だけ。
- **メールアドレス**: 本人が変えるときは他のユーザーと重ならないこと。確認のリンクは、求めたときのアドレスに結び付ける。
  未確認のアドレスは、外部 IdP との結び付け・証明書の対応付け・OIDC の `sub`（email モード）・動的グループの条件に使わない。
- **外に出すメールアドレスは確認済みの値だけ**: ユーザーは今のアドレス（`email`。未確認のことがある）とは別に、最後に確認済みだった
  アドレス（`verified_email`）を持つ。各サービスに渡す値（OIDC の `email`・`sub`（email モード）、式の `user.email`（追加のクレーム・
  SAML の属性と NameID・動的グループの条件）、SCIM の `emails`、API トークン・OAuth で読む `/api/me`、Gravatar）は確認済みの値。
  本人がアドレスを変えても、確認が済むまでは以前の確認済みのアドレスを渡し続け、確認済みのアドレスがなければ渡さない
  （メールアドレスで本人を結び付けるサービスで、他人のアドレスに変えてなりすませないように）。
  管理者が「確認済み」として設定したもの・SCIM・ディレクトリの同期・初期設定・外部 IdP が確認済みとしたものは、そのまま確認済みの値になる。
  自己登録と、外部 IdP が確認済みとしなかったものは未確認。アドレスを消すか、管理者が同じアドレスの「確認済み」を外すと、確認済みの値も消える。
  別の人が同じアドレスを確認済みにしたら、それを以前の値として持っているだけの人（確認待ちの人）からは外す。
  画面（Cookie）の `/api/me`・管理の API は、今の値（`email`・`emailVerified`）と確認済みの値（`verifiedEmail`）の両方を返す。
- **パスワードの再設定のメール**は確認済みのアドレスだけに送る（本人が変えて確認待ちのアドレスには送らない）。
  管理者が画面から送るときは、登録されているアドレスに送る。
- **管理者になるグループ**（自身か親が管理者のグループ）には、動的なメンバーを付けない。SCIM では管理者のユーザー・グループを変えない。
- **Entra**: 許可リストにはテナント ID を書く。メールアドレスは、許可したテナントのときだけ信頼する（マルチテナントでは他のテナントの管理者がメールの属性を書けるため）。
- **ログインの失敗の回数**は、多要素認証まで終わってから戻す。メールのコードの試行は、確認と加算を1つの SQL で行う。
  ロック中はパスワードを確かめず、応答も同じ（ロック中の総当たりを防ぐ）。IP ごとの回数は、IPv6 を /64 にまとめて数える。
  メールでの2つ目の要素は、確認済みのアドレスだけに送る。
- **パスワードの変更（期限切れ・管理者の指定）**は多要素認証の後。多要素の追加（stepUp）では求めない。
  パスワードを変えたら、ほかのログインと、offline_access を含むトークンを失効させる。
- **認可の要求の印**（同意した・アカウントを選んだ）は、ブラウザのセッションとユーザーに結び付ける。再認証（prompt=login・ForceAuthn）は、要求の後にログインしたかを認証の時刻で判定する。
- **認可コード**は、持ち主のクライアントにしか見えない。コードから出したリフレッシュトークンはコードごとの系列にし、
  再利用のとき（期限の後でも）はその系列（offline_access も）と、同じアプリ・ユーザーのアクセストークンを失効させる。
- **ログインの終わり**: ログアウト・無操作・期限切れ・管理者の操作のどれでも `Directory.endLogin` を通し、トークンの失効と
  バックチャネルのログアウトを必ず一緒に行う。リフレッシュは、結び付いたログインが続いているときだけ。
  UserInfo・イントロスペクションは、アプリの無効化とアクセスグループからの除外をすぐ反映する。
- **ログアウト**: OIDC は `id_token_hint` がない GET では確認を挟む。SAML は署名のない要求なら SessionIndex が必須。
  SAML の SessionIndex は SP ごとに違う値（ほかの SP のものを推測できない）。署名付きで SessionIndex がない要求は、NameID が
  使用中のアカウントのものと同じときだけ。実際にログアウトしたときだけ Success を返す。
  ほかのサイトからの POST には SameSite=Lax の Cookie が付かないので、Cookie がなければ同じサイトから POST し直す。
- **SAML の要求**は IssueInstant が必須で、±300 秒まで。応答とアサーションの少なくとも一方は署名する。ACS・SLO は http(s) だけ。
- **SAML の HTTP-Redirect**: 署名を確かめるのと同じ解析で値を取り出し、キーの重複（符号化したキーを含む）を拒否する。SHA-1 は受け付けない。
- **SCIM**: 管理者の所属は SCIM では変えない（グループのメンバーの置き換えでも残す）。フィルターは 4096 文字・かっこ 32 段まで。
- **アプリのアイコンの自動取得**（`SiteIcon`）: アプリを作ったとき・「サイトのアイコンを取得」のとき、起動の URL（なければリダイレクト URI・ACS）の
  トップページの `<link rel="icon">`・`apple-touch-icon`、なければ `/favicon.ico` を取る。https（開発用の http://localhost を除く）だけで、
  リダイレクトの先も同じ条件・3回まで、1回5秒・全体12秒・512KB まで。画像の種類は中身で判定し（PNG・JPEG・GIF・WebP・ICO・SVG）、
  SVG はロゴと同じ検査をする。取れなくてもアプリの作成は成功させる。社内のアプリを想定して、プライベートの IP アドレスは拒否しない。
- **外部への通信**: 上流の IdP の issuer・設定で返る URL は https だけ（開発用の http://localhost を除く。ホストで判定する）。
  issuer か種類を変えたら、シークレットの入れ直しを求める。Google の token_uri は既定のものだけ。応答は 32MB まで。
- **CSP**: 画面のスクリプトは `'self'` だけ（インラインのスクリプトを許さない）。公開の URL が https なら HSTS を付ける。
- **起動の検査**: 本番（DEV_MODE でない）では、APP_SECRET・DATABASE_PASSWORD が例示の値（change-me）なら起動しない。
